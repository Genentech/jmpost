# jmpost repository guide

## Purpose

`jmpost` is an R package for Bayesian joint models that combine:

- a parametric time-to-event (survival) submodel;
- a linear or nonlinear mixed-effects longitudinal submodel for a continuous
  marker, primarily tumour-size trajectories; and
- one or more association/link terms connecting the longitudinal trajectory to
  survival.

The R layer builds data and model specifications, renders a complete Stan
program, compiles it with `cmdstanr`, samples it, and provides posterior
quantities, simulation, scoring, and plotting helpers. The package requires
`R >= 4.1` and is not yet on CRAN.

## Repository map

- `R/`: package implementation. Most domain objects are S4 classes with public
  constructors plus S3 methods/generics.
- `inst/stan/base/`: shared Stan templates and functions used to assemble a
  joint model.
- `inst/stan/lm-*/`: built-in longitudinal-model modules. Directories ending in
  `-cov` are covariate-enabled variants.
- `inst/stan/sm-*/`: built-in parametric survival-model modules.
- `tests/testthat/`: testthat edition 3 tests, generally named after the R class
  or feature under test. `tests/testthat/models/` contains Stan fixtures.
- `vignettes/`: Quarto user guides and custom-model Stan examples.
- `data/` and `R/data.R`: packaged example datasets and their documentation.
- `data-raw/`: source files and scripts used to create packaged data.
- `man/` and `NAMESPACE`: generated by roxygen2; do not edit by hand.
- `README.Rmd`: source for generated `README.md`; edit the Rmd, then regenerate.
- `design/`: exploratory, design, debugging, and legacy material; it is excluded
  from package builds and from Air formatting.
- `.github/workflows/`: reusable CI workflows for checks, coverage, docs,
  linting, spelling, links, dependency audit, and releases.

## Main object and execution flow

1. `DataSubject`, `DataSurvival`, and `DataLongitudinal` validate and harmonise
   user data; `DataJoint` combines them and converts them to Stan data.
2. A longitudinal model (`LongitudinalGSF`, `LongitudinalSteinFojo`,
   `LongitudinalClaretBruno`, `LongitudinalRandomSlope`, and covariate variants),
   a survival model (`SurvivalExponential`, `SurvivalGamma`,
   `SurvivalLoglogistic`, or `SurvivalWeibullPH`), and `Link` components are
   composed by `JointModel`.
3. `Parameter`, `Prior`, and `ParameterList` define declarations, priors, and
   initial values. `Promise` objects defer link/model details until composition.
4. `StanModule` parses and merges Stan blocks. `as.StanModule.JointModel()`
   renders `inst/stan/base/base.stan` with `jinjar` and combines component
   modules. `compileStanModel()` caches compiled executables by a digest of the
   generated Stan code.
5. `sampleStanModel()` returns `JointModelSamples`. Quantity generators and grid
   classes drive generated quantities for subject, population, and prediction
   use cases.

When changing a model, inspect both its `R/<Model>.R` implementation and the
matching `inst/stan/<model>/` directory. Changes to shared rendering or data
contracts can affect every model, so include focused rendering/data tests as
well as the model-specific test.

## Development conventions

- Follow the existing four-space R style. `air.toml` sets an 80-column line
  width and excludes `design/`; format R code with `air format <paths>` when Air
  is available.
- Preserve the package's British English spelling (`Language: en-GB`). Add
  intentional specialist terms to `inst/WORDLIST` if spelling CI requires it.
- Public APIs and S3 methods are documented with roxygen comments in `R/`.
  This project also uses `roxytypes` typed tags such as `@typed`.
- Regenerate documentation after changing exports, signatures, classes, or
  roxygen text; never patch `NAMESPACE` or `man/*.Rd` directly.
- `DESCRIPTION` has an explicit `Collate` order. New R files may need to be
  placed there according to their class/generic dependencies; existing files
  also use roxygen `@include` declarations.
- Keep R-side names, dimensions, and declarations synchronized with Stan-side
  templates. Prefer composing `StanModule`s over duplicating shared Stan code.
- Use `read_stan()` for packaged Stan fragments and `decorated_render()` for
  Jinja-style templating, consistent with existing modules.
- Add regression tests in the closest matching `test-*.R` file. Use a small
  dedicated fixture under `tests/testthat/models/` only when the Stan source is
  itself part of the behavior under test.
- Do not commit compiled Stan executables, generated CmdStan source, R check
  directories, rendered vignettes, or local caches.

## Testing and validation

Use the narrowest useful check first, then broaden it in proportion to the
change. Typical commands from the repository root are:

```sh
Rscript -e 'pkgload::load_all(helpers = FALSE, quiet = TRUE); testthat::test_file("tests/testthat/test-<feature>.R")'
Rscript -e 'devtools::test()'
Rscript -e 'devtools::document()'
Rscript -e 'devtools::check()'
```

Notes:

- Tests run with testthat edition 3 and parallel testing enabled.
- Stan compilation/sampling requires `cmdstanr` plus a working CmdStan install.
  `R/zzz.R` recognizes `CMDSTAN` and `CMDSTAN_PATH`.
- Set `JMPOST_CACHE_DIR` to reuse compiled Stan models across runs. Otherwise a
  session-specific temporary directory is used.
- Many expensive comparison, compilation, and sampling tests are guarded by
  `JMPOST_FULL_TEST=TRUE`; routine local tests intentionally skip those cases.
- Visual snapshot updates/checks are controlled by
  `JMPOST_GRAPH_SNAPSHOT=TRUE`.
- CI uses `NOT_CRAN=TRUE` and CmdStan environment variables. The scheduled
  workflow enables both full tests and graph snapshots.
- For Stan-template changes, useful focused coverage includes
  `test-StanModel.R`, `test-StanModule.R`, `test-jinjar_render.R`,
  `test-stan_functions.R`, and the affected model's test file.

## Documentation and examples

- The quickest package overview and end-to-end example is in `README.Rmd`.
- `vignettes/quickstart.qmd` covers normal fitting; `statistical-specification.qmd`
  explains the model; `extending-jmpost.qmd` and the custom-model vignettes
  cover extension points.
- Keep examples lightweight. Sampling or compilation examples that are not
  appropriate for routine checks should remain guarded (for example with
  `\dontrun{}` in roxygen examples).
- Pkgdown configuration lives in `_pkgdown.yml`; Quarto is the vignette builder.

## Code reviews

For every requested code review or pull-request review, load and follow the
repository's `critical-code-reviewer` skill before inspecting the change. Use
that skill's severity, evidence, testing, and reporting guidance, and prioritize
correctness, statistical/Stan behavior, security, accessibility where relevant,
maintainability, tests, and edge cases.

During review, pay particular attention to R/Stan contract mismatches, incorrect
parameter constraints or dimensions, numerical stability, generated-quantity
behavior, class validity, optional survival-only or longitudinal-only models,
and whether expensive paths have an appropriate test strategy.
